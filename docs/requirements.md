# 並列AIエージェント統合管理ダッシュボード 要件定義書

> バージョン: 0.1.0  
> 作成日: 2026-03-31  
> ステータス: Draft

---

## 1. プロダクト概要

### 1.1 プロダクト名（仮）
**AgentGrid**（または Orchid / FleetAI 等、TBD）

### 1.2 一言で言うと
「複数の Claude Code / Gemini CLI エージェントを一つのローカルダッシュボードから統合管理するオーケストレーター」

### 1.3 解決する課題
| 現状の課題 | AgentGrid による解決 |
|---|---|
| 並列エージェントの状態が各ターミナルに分散 | 単一WebUIで全エージェントを一覧監視 |
| タスク割り当てが手動・属人的 | タスクキューからエージェントへ自動アサイン |
| エージェント間のコンフリクトが起きやすい | git worktree ＋ ロック機構で衝突防止 |
| コストが見えない | トークン消費・APIコストをリアルタイム表示 |
| 非エンジニアには使えない | WebUIで操作可能（CLIレスも目標） |

## 2. アーキテクチャ概要

```
┌─────────────────────────────────────────┐
│          AgentGrid Dashboard (Web UI)    │
│  [タスク管理] [エージェント監視] [コスト] │
└────────────────┬────────────────────────┘
                 │ WebSocket / REST
┌────────────────▼────────────────────────┐
│       Orchestrator Server (Node.js)      │
│  タスク分配 / ロック管理 / 結果集約       │
└──┬───────────┬──────────────┬───────────┘
   │           │              │
   ▼           ▼              ▼
[Agent 1]  [Agent 2]  ...  [Agent N]
Claude Code / Gemini CLI
(git worktree で隔離)
```

### 2.1 主要コンポーネント

| コンポーネント | 技術スタック（案） | 役割 |
|---|---|---|
| Dashboard UI | React / Vite | エージェント状態可視化・操作 |
| Orchestrator | Node.js / Express | タスク分配・エージェントプロセス管理 |
| Agent Runner | child_process / PTY | Claude Code / Gemini CLI の起動・通信 |
| Task Store | SQLite（ローカル） | タスクキュー・実行ログ永続化 |
| Lock Manager | ファイルベース or Redis | タスクの排他制御 |

## 3. 機能要件

### 3.1 タスク管理

| ID | 機能 | 優先度 |
|---|---|---|
| TM-01 | タスクをカード形式で作成・編集・削除 | Must |
| TM-02 | タスクに担当エージェント種別を指定（Claude / Gemini / Any） | Must |
| TM-03 | タスクのステータス管理（未着手 / 実行中 / 完了 / 失敗） | Must |
| TM-04 | タスクの依存関係定義（タスクBはタスクA完了後に開始） | Should |
| TM-05 | タスクへのファイル・コンテキストの添付 | Should |
| TM-06 | タスクのバッチインポート（YAML / JSON） | Could |

### 3.2 エージェント管理

| ID | 機能 | 優先度 |
|---|---|---|
| AM-01 | エージェントの起動・停止・再起動 | Must |
| AM-02 | エージェント種別の設定（Claude Code / Gemini CLI） | Must |
| AM-03 | 同時起動数の上限設定 | Must |
| AM-04 | 各エージェントへの作業ディレクトリ（worktree）自動割り当て | Must |
| AM-05 | エージェントのターミナル出力をリアルタイム表示 | Must |
| AM-06 | エージェントへのメッセージ送信（割り込み指示） | Should |
| AM-07 | エージェントのプロファイル保存（よく使う設定の再利用） | Could |

### 3.3 監視・可視化

| ID | 機能 | 優先度 |
|---|---|---|
| MV-01 | 全エージェントのグリッドビュー（画像1のような一覧） | Must |
| MV-02 | エージェントごとのスコアカード表示（画像2のような評価） | Must |
| MV-03 | スコア項目：実装完了度 / コード品質 / セキュリティ / UX / テスト | Must |

| MV-05 | タスク完了率のプロジェクト全体サマリー | Must |

### 3.4 コスト管理

| ID | 機能 | 優先度 |
|---|---|---|
| CM-01 | エージェントごとのトークン消費数表示 | Must |

| CM-03 | プロジェクト全体のコスト上限アラート設定 | Should |

| ID | 機能 | 優先度 |
|---|---|---|

| GI-03 | タスク完了時のブランチマージ支援（PR作成リンクなど） | Could |

### 3.6 ダッシュボード自動生成（将来機能）

## 4. 非機能要件

### 4.1 パフォーマンス
- エージェント状態の更新レイテンシ：1秒以内
- 同時管理エージェント数：最大20（ローカル環境標準）

### 4.2 動作環境
- macOS / Linux（Windows は将来対応）
- Node.js 18+
- ブラウザ：Chrome / Firefox 最新版

### 4.3 セキュリティ
- ローカル動作を基本とし、外部通信なし（オフライン対応）
- APIキーは環境変数で管理（UIには表示しない）

### 4.4 スケーラビリティ
- Phase 1：ローカルのみ
- Phase 2：同一LAN内の複数PC対応
- Phase 3：クラウド対応（Ona のようなモデル）

## 5. ユーザーストーリー

```
As a エンジニア
I want 複数のエージェントに異なるタスクをアサインして並列実行したい
So that 一人で複数人分の開発スピードを出せる

As a エンジニア
I want 各エージェントの進捗をリアルタイムで確認したい
So that どのエージェントが詰まっているかすぐ気づける

As a エンジニア
I want APIコストをタスクごとに追跡したい
So that 費用対効果の高いタスク分割を学習できる
```

## 6. スコープ外（v1.0）

- クラウドデプロイ・チーム共有機能
- エージェント間のリアルタイム通信（直接メッセージング）
- 自然言語でのタスク自動分割（AIによるタスク分解）
- モバイル対応

## 8. 技術選定（確定）

| # | 論点 | 決定 | 備考 |
|---|---|---|---|
| 1 | エージェントとの通信方式 | **両方対応（切替可能）** | PTY をデフォルト、SDK をオプションで切替 |
| 2 | タスクのスコアリング | **評価エージェントを別に立てる** | 専用の Judge Agent が完了コードをレビュー |
| 3 | ロック機構 | **ファイルベース** | `.lock` ファイル＋起動時のゴミファイル自動クリーンアップ |
| 4 | UIフレームワーク | **Vue** | Vue 3 + Vite + Pinia |
| 5 | 配布方法 | **npm グローバルインストール** | `npm install -g agentgrid` で即起動 |

### 選定による追加設計方針

**通信レイヤーの抽象化**
```
AgentRunner（インターフェース）
├── PTYRunner     ← Claude Code / Gemini CLI をプロセス起動
└── SDKRunner     ← Anthropic SDK / Google GenAI SDK を直接呼び出し
```
設定ファイル（`agentgrid.config.json`）の `runner` フィールドで切替。

**Judge Agent の動作フロー**
```
Worker Agent タスク完了
      ↓
Judge Agent 起動（別 worktree）
  ├── 差分コードを読み込み
  ├── 実装完了度 / コード品質 / セキュリティ / UX / テスト を採点
  └── スコアを JSON で Orchestrator に返却
      ↓
Dashboard にスコアカード反映
```

**ファイルロックのクラッシュ対策**
- `.lock` ファイルに PID を記録
- Orchestrator 起動時に存在する `.lock` の PID が生きているか確認し、死んでいれば自動削除
